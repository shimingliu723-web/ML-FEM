> 验证日期：2026-10-10

> 代码版本：`main-platform-20261008`（提交 `69a007a`）

---

## 1 为什么要做这个

选题要求 9 要求"跨环境验证"，此前状态是"只有一种环境"。另外演示环境很可能连不上
校园网和队伍服务器，所以需要证明作品在本地环境同样可用。

这次验证同时回答两个不同的问题，**必须分开看**：

| 问题 | 关注点 |
| --- | --- |
| **功能是否跨环境可用** | 同一份代码在不同发行版、内核、编译器、Python 版本上能否正确构建并工作 |
| **结论是否跨环境可复现** | 计时检出、修复闭环这类依赖测量的结论，换环境后是否还成立 |

## 3 验证方法

新增 `xenv_validate.py`，位置无关、只用标准库（兼容 Python 3.8），依次执行 10 项检查：

| 检查 | 内容 |
| --- | --- |
| `build` | `make all` 构建三个参数集的平台库与计时程序 |
| `targets` | 八个目标实现（基线/对照/修复）各自构建，共 24 个动态库 |
| `basic` | ML-KEM-512/768/1024 加解密自测各 20 轮 |
| `vector` | mlkem-native 自带公开测试向量逐项比对 |
| `samples` | 生成四类等长样本，校验翻转位置与长度不变 |
| `timing_stats` | 对照实现计时 + 统计分析，**跑 3 轮看检出率** |
| `code_location` | 源码级定位与修复前后源码 diff |
| `binary_location` | 反汇编 `mlkem_dec`，统计条件跳转/cmov/setcc |
| `repair_closure` | 自动生成修复目标、复测、输出前后对比 |
| `desktop` | 桌面版语法、依赖与启动脚本齐备性 |

判定原则：**能跑通不等于结论成立**。所以 `timing_stats` 与 `repair_closure` 额外记录
`flow_ok`（流程是否跑通）与 `detected`（是否检出），把"功能可用"和"结论可复现"分开。

## 5 结论一：功能层面跨环境完全一致

**七项检查在三个环境上全部通过**，且结果数值一致：

**公开测试向量**：三个环境都是 **15/15 项通过**，覆盖 ML-KEM-512/768/1024 的
确定性 keygen、确定性 encaps 与 decaps，与 `expected_test_vectors.h` 逐项匹配。

**样本生成**：三个环境都生成 4 条记录、四类样本（`normal` / `changed_mid` /
`changed_first` / `changed_last`）、密文长度恒定 768 字节（ML-KEM-512），
翻转位置全部正确。

**二进制定位**：**三个环境结果完全相同**——

| 目标 | 条件跳转 | cmov | setcc |
| --- | ---: | ---: | ---: |
| `variant_early_return` | **7** | 0 | 0 |
| `variant_repaired` | 6 | 0 | 0 |
| `mlkem_native_baseline` | 6 | 0 | 0 |

这一点价值很高：它是 gcc 9.4.0 与 gcc 13.3.0 两种编译器、三种执行环境下各自编译出来的
产物，条件跳转计数仍然一致。说明"早退对照版本比基线多一条条件控制流"这个定位结论
**不依赖具体编译器版本**。

**构建**：八个目标 × 三个参数集 = 24 个动态库，三个环境全部构建成功，编译零警告
（`-Wall -Wextra -Wpedantic`）。

> 结论：作品可以在不依赖服务器与校园网的本地环境运行，满足要求 9 的可用性部分。

## 6 结论二：计时检出能力对环境高度敏感（本次最重要的发现）

对照实现的真实效应稳定在约 **−300 ns**（changed 输入比 normal 快，符合早退机理）。
三个环境各跑 3 轮、每轮 2000 对配对，结果差别很大：

| 环境 | 检出轮数 | 三轮均值差（ns） | 评价 |
| --- | ---: | --- | --- |
| 服务器 | **3 / 3** | −242 / −297 / −238 | 方向一致、幅度集中，可靠 |
| WSL2 | **0 / 3** | −741 / −248 / −149 | 方向对但幅度失控 |
| 虚拟机（第一次） | **0 / 3** | **+113 / +557 / +98** | **符号反了** |
| 虚拟机（第二次，同一环境重跑） | **0 / 3** | **−449 / −195 / −592** | **符号又对了，但仍未检出** |

**同一个虚拟机、同一份代码、同一套参数，两次完整重跑得到相反符号**（第一次全正、
第二次全负）。这是比幅度失控更强的证据：结果**不可复现**，不能归因于随机误差。

服务器三轮幅度落在 238~297 ns 区间内，与真实效应吻合。

**不是样本量不够的问题。** 在 WSL 上做了样本量扫描：

| 每轮配对 | 300 | 1000 | 3000 | 10000 | 20000 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 均值差（ns） | +1096 | −228 | +75 | −451 | +100 |
| 是否检出 | 否 | 否 | 否 | 是 | 否 |

样本量从 300 加到 20000，均值差在 **±1000 ns 之间反复变号**，只在 10000 处偶然命中一次。
如果是随机噪声，增加样本量应该让结果收敛；这里的表现是**不收敛**，说明存在持续的
系统漂移，而不是可平均掉的随机误差。

**原因分析**（按可能性排序）：

1. **无法控制 CPU 频率**。服务器能读到并且固定在 `powersave`，WSL 与虚拟机读不到
   cpufreq，频率由 Windows 主机动态管理，高低频切换带来的差异与效应同量级。
2. **异构核心**。i9-14900HX 是性能核 + 能效核的混合架构，绑定到 cpu0 不代表每次都跑
   在同一个核上，也不代表不是被调度的能效核。
3. **虚拟化层级**。WSL2 与 VMware 都引入 vCPU 调度抖动，效应只占解封装总时长
   （约 31 µs）的 1%，很容易被抖动淹没。

**这不影响平台的功能正确性**，但直接影响结论的适用范围：

> **计时类结论只在专用服务器上有效，桌面/虚拟机环境不能用来做精确计时实验。**

这一条正好解释了为什么平台要单独做桌面版：桌面版是**功能演示与结果展示**载体，
不是精确计时载体。建议在桌面版界面和报告里明确标注这一点，避免演示时被质疑
"为什么本地跑出来和报告不一样"。

## 7 结论三：修复闭环的可用性分级

| 环境 | 流程跑通 | 闭环成立 | 实测 |
| --- | --- | --- | --- |
| 服务器 | 是 | **是** | 修复前 −271 ns（可区分）→ 修复后 −2 ns（不可区分） |
| WSL2 | 是 | 否 | 修复前 896 ns（不可区分）→ 修复后 273 ns（不可区分） |
| 虚拟机 | 是 | 否 | 修复前 645 ns（不可区分）→ 修复后 −522 ns（不可区分） |

**三个环境的修复流程全部跑通**：都能自动识别早退模式、生成修复目标、产出
`repair.patch` 与 `repair_report.json`、构建、复测。这部分与结论二无关，是可靠的。

**只有服务器能得出闭环成立的结论**。WSL 与虚拟机上前后都判不出差异，
所以"修复是否生效"在这两个环境里**没有得到验证**——不能说修复失效，只能说测不出来。

虚拟机重跑一次后，修复前从 +645 ns 变成 −304 ns，修复后从 −522 ns 变成 −36 ns，
两次符号都不同，进一步说明该环境下的数值不具备可解释性。

## 8 结论四：桌面版的环境依赖（已解决）

首次验证时虚拟机报 `ModuleNotFoundError: No module named 'tkinter'`。
原因是 Ubuntu 默认不安装 `python3-tk`（服务器与 WSL 恰好已装，所以之前没暴露）。

补装后重跑，**虚拟机桌面版检查从 warn 变为 pass**：

```bash
sudo apt install python3-tk
```

| 环境 | 补装前 | 补装后 | DISPLAY |
| --- | --- | --- | --- |
| 服务器 | pass | pass | 未设置 |
| WSL2 | pass | pass | `:0`（WSLg） |
| 虚拟机 | **warn** | **pass** | 未设置 |

> **部署建议**：演示环境如果是新装的 Ubuntu，需要在部署说明里写上
> `sudo apt install python3-tk` 这一步，否则现场演示桌面版会直接起不来。
> 这是一个只能靠跨环境验证发现的问题——在服务器上永远碰不到。
> 另外 WSLg 提供了 `DISPLAY=:0`，是三个环境里唯一能真正弹出窗口的。

## 11 遗留问题

1. `formal_timing.py` 的 CI 判定（`statistically_distinguishable`）与
   `stats.py` 的正式检验**会出现结论不一致**——实验中在虚拟机的某次运行里出现
   CI 显示可区分、而正式检验判为不可区分。这两个口径需要统一，或至少显式标注冲突。
2. 通用环境缺少频率控制手段，建议在 `env_report.py` 里增加"本环境是否适合做计时实验"
   的环境自检项，让平台自己给出提示，而不是让使用者事后发现。
