更新时间：2026年10月7日  
项目目录：`/disk4/lsm/A1-13-MLKEM-Platform`  
当前目标：先把平台主干做成可演示、可复现、可继续扩展的工程框架，后续再逐步补强定位、修复、报告和实验数据。

## 1. 项目现在到底在做什么

本项目不是只写一个 ML-KEM 算法，也不是只做一个孤立实验，而是做一个面向 ML-KEM 实现的检测与实验平台。

平台要完成的核心事情是：

1. 接入一个或多个 ML-KEM 实现；
2. 验证它们的基本算法流程是否正确；
3. 自动生成不同类别的测试输入；
4. 对解封装过程进行高精度重复计时；
5. 用统计方法判断不同输入类别的运行时间是否有明显差异；
6. 如果发现差异，进一步定位可能来源；
7. 给出修复思路或修复版本；
8. 再做一次前后对比实验，说明修复效果和性能开销；
9. 最终生成可复现的实验记录和报告材料。

一句话概括：我们做的是一个“ML-KEM 实现检测平台”，平台本身可以接入不同版本的 ML-KEM，并对它们进行正确性验证、样本生成、计时检测、定位、修复对比和报告整理。

## 3. 当前平台已经具备的模块

### 3.1 基础 ML-KEM 功能模块

目标：对应题目第 1 条“基本密码功能”。

当前已实现：

- 支持 ML-KEM-512、ML-KEM-768、ML-KEM-1024；
- 支持密钥生成、封装、解封装三类基础操作；
- 支持运行自测，输出每个安全等级的通过次数和平均耗时；
- 支持接入不同目标实现，而不是只能测平台内置实现；
- 支持公开测试向量或自定义向量输入；
- 支持批量输入向量并输出逐条验证结果；
- 向量验证结果只展示摘要和是否匹配，不直接暴露敏感完整数据。

目前已通过的基础自测结果：

```text
ML-KEM-512: 20/20 passed
ML-KEM-768: 20/20 passed
ML-KEM-1024: 20/20 passed
```

这个模块后续要继续优化的重点：

- 前端结果展示要更清楚，让评委看到“输入是什么、检查了什么、为什么算通过”；
- 补充公开测试向量来源说明；
- 支持上传或粘贴批量测试向量；
- 支持导出验证报告。

### 3.2 目标实现接入模块

目标：让平台能够检测不同 ML-KEM 实现，避免看起来只是“自己测自己”。

当前已实现：

- 平台维护一组待测目标；
- 每个目标可以配置名称、类型、描述、支持等级、动态库路径模板；
- 已支持通过前端注册本地实现；
- 已支持构建目标和自测目标；
- 后端 API 已经能按照目标 ID 加载对应动态库。

当前内置目标：

```text
mlkem_native_baseline   规范基线实现
variant_early_return    对照实现，用于展示平台能发现明显时间差异
variant_fixed           修复后对照实现，用于展示前后对比效果
```

注意：`variant_early_return` 不应该作为最终算法质量代表，它只是用来证明平台的检测、定位、修复对比流程有效。

### 3.3 自动生成测试样本模块

目标：对应题目第 3 条“输入分类与测试”，以及高水平作品中的“自动生成测试样本”。

当前已实现：

- 选择目标实现和安全等级；
- 自动生成正常输入；
- 自动生成若干类等长变体输入，例如中间字节改变、首字节改变、末字节改变；
- 保存样本 CSV 和 JSON 文件；
- 保留样本生成参数，便于复现实验。

当前生成结果保存位置：

```text

```

后续要继续优化：

### 3.4 高精度时间检测模块

目标：对应题目第 2、4、7、8、9 条。

当前已实现：

- C 语言计时程序，只测目标实现的解封装函数；
- 使用 `CLOCK_MONOTONIC_RAW` 采集时间；
- 支持固定 CPU 核运行；
- 支持预热；
- 支持多轮重复实验；
- 支持随机化测试顺序，降低顺序偏差；
- 输出原始 CSV 数据和 JSON 分析结果；
- 统计指标包括均值、标准差、P05、P50、P95、均值差、95% 置信区间、t 统计量等；
- 支持防护前后在相同或等价环境下复测。

当前结果保存位置：

```text
/disk4/lsm/A1-13-MLKEM-Platform/results/formal_timing/
```

这个模块目前的正确理解：

- 对规范基线实现，检测不到明显差异是合理的；
- 对专门准备的对照实现，平台应该能检测出明显差异；
- 对修复后实现，差异应该明显降低；
- 平台价值不是证明所有实现都有差异，而是证明它能对不同实现进行检测和复测。

## 5. 当前最适合展示给评委的完整流程

1. 进入“基础 ML-KEM 功能实现”；
2. 展示 ML-KEM-512/768/1024 自测全部通过；
3. 粘贴或导入测试向量，展示批量验证结果；

6. 进入“时间检测”，选择对照实现并运行重复实验；
7. 展示统计结果和明显差异判断；
8. 进入“代码定位”，展示平台定位到可疑代码位置；
9. 进入“修复对比”，展示修复前后代码差异；
10. 重新运行检测，展示差异降低；
11. 进入“性能评估”，展示修复前后平均耗时和分位数；
12. 进入“报告复现”，生成可复现实验报告。

这个流程能完整覆盖题目要求中的“检测—定位—防护—复测—性能—复现”。

## 8. 当前需要注意的问题

1. 不要把平台说成“只检测自己的 ML-KEM”。正确说法是：平台接入不同 ML-KEM 实现进行检测，内置实现只是演示目标。
2. 对规范实现没有检测到明显差异是合理结果，不是失败。
3. 对照实现用于证明平台检测能力，修复实现用于证明防护效果。
4. 正式报告中不要只写“有差异”或“没差异”，必须展示样本数量、统计指标和实验环境。
5. 计时实验受系统噪声影响，最终数据要固定 CPU 核、增加样本数量，并保留原始数据。
6. 性能开销可能因为噪声出现负值或波动，正式报告里要用多轮实验和分位数说明。
