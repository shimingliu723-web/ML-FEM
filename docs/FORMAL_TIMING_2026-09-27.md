# 正式解封装计时实验记录 2026-09-27

## 实验对象与问题

本次测量对象是平台使用的 `mlkem-native` 原生库，不是独立参考短实验。比较同一解封装函数处理两类等长输入的运行时间：正常生成的输入，以及在对应输入中间字节翻转一位后的输入。每组长度相同，事先确认正常输入的输出与封装端一致、变化后的输出不同。比较的目标是判断当前实现与当前条件下是否存在可重复的时间差异。

## 环境与方法

- 服务器：Intel Xeon Gold 6234，Ubuntu 20.04.6，Linux 5.4.0-216-generic。
- 编译：GCC 9.4.0，核心库和计时程序均使用 `-O3`。
- CPU：固定在逻辑核心 2；频率管理策略为 `powersave`。未修改系统策略。
- 参数集：ML-KEM-512、768、1024；每组各重复独立运行 3 轮。
- 每轮：生成 32 组配对输入，预热 2000 组，再采集 30000 组配对数据。每组的两类输入随机安排先后顺序。
- 计时：C 程序使用 `CLOCK_MONOTONIC_RAW`，计时区间仅包围 `mlkem_dec`。原始记录按次保存，未事后剔除异常值。
- 复核：每 200 组组成一个时间块，块内分别求两种先后顺序的差值均值，再平均以平衡顺序影响。区间是 150 个时间块的均值正态近似 95% 区间；应结合独立重复轮次解释，不能把单轮显著性当作最终结论。
- 原始 CSV 和每轮 JSON 留在服务器 `/disk4/lsm/A1-13-MLKEM-FormalTiming/results/formal_timing/`。

## 结果

表中差值为“变化后的输入耗时减正常输入耗时”，单位纳秒。平均解封装耗时大约为 31–33、48、72–74 微秒，分别对应三个参数集。

| 参数集 | 轮次 | 顺序平衡后的均值差 ns | 95% 区间 ns |
| --- | ---: | ---: | ---: |
| 512 | 1 | -1.54 | [-8.53, 5.45] |
| 512 | 2 | -2.25 | [-7.77, 3.28] |
| 512 | 3 | 3.02 | [-2.91, 8.95] |
| 768 | 1 | 9.40 | [2.86, 15.93] |
| 768 | 2 | -14.65 | [-79.09, 49.80] |
| 768 | 3 | -3.96 | [-10.09, 2.18] |
| 1024 | 1 | -5.69 | [-14.66, 3.27] |
| 1024 | 2 | -57.85 | [-127.62, 11.93] |
| 1024 | 3 | -2.60 | [-25.84, 20.64] |

512 的三个区间均跨零。768 只有第一轮区间未跨零，随后两轮没有复现同方向、同规模的差异。1024 的三个区间均跨零。因此，目前没有获得稳定、可重复的两类输入时间差异。个别原始数据有较大的运行波动，且两种测量先后顺序能带来几十纳秒的偏移；这也是采用块内顺序平衡和多轮复核的原因。

## 机制依据与解释边界

FIPS 203 的解封装流程包含重新计算、比较以及验证失败时的隐式拒绝。当前 `mlkem-native` 的 `kem.c` 在比较后继续计算结果，再调用 `mlk_ct_cmov_zero` 做结果选择；`verify.h` 中的 `mlk_ct_memcmp` 遍历固定长度，并采取措施避免编译器提前结束比较。这些源代码设计与本次未观察到稳定差异的结果一致，但不能仅凭源码或有限次计时证明所有机器、编译器、输入类别下绝对恒定时间。

后续若要为竞赛展示完整的“发现—定位—改进—复测”链路，应准备一个**明确标注为教学对照、与正式实现分离**的可变时间版本，再用相同采样与统计流程比较改进前后。不得把本次参考实现的短实验结果混作 `mlkem-native` 的正式测量结论。

依据：[NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)；仓库 `core/mlkem-native/mlkem/src/kem.c` 和 `core/mlkem-native/mlkem/src/verify.h`。
